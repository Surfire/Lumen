Measured 2026-11-25 UTC on Apple M5 Max, 128 GiB RAM, macOS 27.0.1 arm64, AC power. This is **persistent CLI transport**, not launcher UI, full-text, or competitor timing.

Use fresh work directories to reproduce **first-scan** timing. Reusing a retained directory restores the known synthetic update batch, but an existing database makes the next scan a reconciliation, not first creation. `--scan-only` followed by `--reuse-index` can separate scanning from querying; do not reuse an index after a completed update benchmark. The actual final runs removed only the synthetic SQLite database/sidecars before rescanning the staged corpus, so the reported scans are first database creation with a warm filesystem cache. Corpus generation happened beforehand and is excluded; its duration was not retained for these final runs (`generation_ms: null`).

## Methodology and correctness

- Real APFS files, not injected database rows or an in-memory-only corpus. Each scale has exactly 100,000 / 1,000,000 empty workload files across 100 directories, plus the root and **two additional readiness controls**. One quarter of workload names use seven Chinese prefixes; others use `case`. All have unique seven-digit IDs and `-alpha report.txt` suffixes. No private data is read.
- Scan command: `lumen --db INDEX index --root CORPUS --separate-content`. No `--documents`, content extraction, embedding, or model. Both scans report `documents=0`, `documents_not_read=0`, no unreadable entries, and zero fallback directories.
- One `lumen serve` process per scale, JSONL `mode=name`, Top-20. Time starts before writing/flushing a request and ends after reading/parsing the complete reply: Python, pipe transport, engine, and JSON decode are included. Process launch and initial load are excluded from hot timings and reported separately.
- **Deterministic hot-index proof:** two equally prefix-matching control files have fixed mtimes (2000-01-01 and 2025-01-01). SQL fallback orders the shorter old file first; SoA ranks the longer newer file first. Measurement waits for that observable RAM-only ordering, then warms all queries and requires four one-second RSS/latency plateau samples. This is not just an assumption that the first reply means RAM is ready.
- Four classes, each with 50 distinct queries, 20 repetitions: 1,000 samples/class, 4,000/scale. Interleaved shuffle uses seed 404. Examples: `case-0000101`, `代谢研究-0000000`, `daixieyanjiu0000000`, `0000101 report`. Pinyin spelling omits punctuation because the indexed transliteration does. These are selective ID-bearing queries, **not** broad single-character/high-fanout tests.
- Every warmup and measured request asserts the expected exact synthetic path is in the returned Top-20; request IDs must match. All 4,000 measured requests passed at each scale. This validates known-path recall, not a complete ranking-quality benchmark.
- Percentiles: median p50; nearest-rank p95/p99; milliseconds. No failed/empty expected results are counted as successful fast queries.
- RSS is macOS `ps -o rss= -p PID`, KiB, for the entire serve process (SQLite plus RAM index and runtime), not virtual size or an index-only allocation estimate. Warm RSS was unchanged across all four stabilization windows; the additional 4,000 queries increased it by only 32 KiB / 16 KiB at the two scales. Concurrent samples are taken at start/every 1,000 queries and again at end: **not a measured peak**. Scanner-process RSS and initial scan peak are not measured.

## Concurrent filesystem updates

A worker creates 100 files, renames 100 existing files, deletes 100 existing files, then runs **one explicit full name-only filesystem rescan** while the same serve process answers the shuffled query stream. No direct SQL insertion, fake events, or per-query subprocesses. The measured foreground queries target unchanged paths and assert exact-path recall throughout; after completion, the still-running serve must expose a created path and renamed destination, omit the old source, and omit a deleted path. All checks passed at both scales.

This is deliberately a **rescan contention/refresh benchmark**, not a native watcher test or a claim of sub-second event-to-visibility SLA. Foreground sampling lasts only while the writer is active, so counts differ and do not reach 20 repetitions/query. Timings may include fallback/reload behavior while the snapshot is invalidated; no hot-only claim is made for this phase. The writer wall time includes the mutation batch, scanner startup, metadata traversal, and commit; final result-visibility polling is outside that number.

## Scope of conclusions

For this selective synthetic corpus, the actual compact SoA was confirmed ready at both scales. Million-file hot name and multiword p95 are below 1 ms including transport, observed serve RSS is below 150 MiB even after updates, and concurrent-rescan p95 remains below 40 ms for all four classes. These observations do not establish a universal 150 MiB peak bound, broad-query performance, idle energy use, native watcher latency, launcher first-frame latency, real cloud-provider behavior, semantic/full-text quality, or superiority over Spotlight/Tinycast; none was measured here.

Validation: Python syntax/help checks and real end-to-end scans, RAM-readiness proof, 8,000 hot exact-path assertions, 3,191 concurrent exact-path assertions, and live create/rename/delete checks across both scales; `cargo fmt --check` also passed. Rust/app-wide gates belong to the integrating engine coordinator; this task changes only the benchmark and this report.
